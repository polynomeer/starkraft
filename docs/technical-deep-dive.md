# Technical Deep Dive

## 문서 목적

이 문서는 `starkraft`의 기술적 설계 결정을 깊이 있게 설명한다.  
코드 구현을 그대로 나열하기보다, 왜 이런 구조를 택했는지와 각 계층이 어떤 문제를 해결하는지에 초점을 맞춘다.

## 시스템 전체 그림

`starkraft`는 다섯 개의 핵심 계층으로 구성된다.

1. `sim`: 결정론적 규칙 엔진
2. `server`: authoritative orchestration
3. `client`: 입력 및 상태 소비 계층
4. `tools`: 오프라인 검증/분석 도구
5. `shared-protocol`: 계층 간 계약의 기준점

중요한 점은 "게임 로직"과 "전송/표시/운영 로직"을 의도적으로 분리했다는 것이다.

## 왜 결정론이 먼저인가

실시간 전략 게임은 시스템이 복잡해질수록 다음 문제가 커진다.

- 같은 버그가 다시 재현되지 않는다
- 네트워크 불일치 원인을 좁히기 어렵다
- 밸런스 조정의 근거가 약해진다
- 리플레이가 단순 로그로만 남고 검증 자산이 되지 못한다

`starkraft`는 이 문제를 줄이기 위해 규칙 엔진을 고정 tick 결정론 기반으로 설계한다.

### 결정론을 지키는 핵심 규칙

- 시간은 실수 기반 delta가 아니라 정수 tick으로 전진한다
- 시스템 실행 순서를 고정한다
- iteration 순서를 안정적으로 유지한다
- replay command 적용 순서를 명확히 한다
- hash 계산 입력 순서를 통제한다
- 랜덤은 seed와 사용 위치를 통제한다

결과적으로 "같은 입력이면 같은 world hash"라는 기준을 세울 수 있다.

## `sim` 계층 설계

### 역할

`sim`은 게임 규칙의 단일 진실 공급원이다.  
이 계층은 다음을 담당한다.

- 유닛/건물/자원/전투 규칙
- 시야와 안개
- 생산, 건설, 연구
- 승리 판정
- replay/world hash 생성
- 로컬 플레이용 snapshot 출력

반대로 `sim`이 담당하지 않는 것은 아래와 같다.

- websocket IO
- room/session 관리
- 사용자 계정 개념
- 운영용 파일 보관 정책
- UI/HUD 상태

### 왜 ECS-lite 구조인가

전통적 OOP 객체 그래프보다 ECS-lite 구조를 택한 이유는 다음과 같다.

- 상태를 직렬화하고 비교하기 쉽다
- 시스템별 책임이 분리된다
- hash 계산과 replay 재적용에 유리하다
- 특정 규칙만 독립 테스트하기 좋다

이 프로젝트의 목적은 "객체 모델링의 우아함"보다 "재현성과 추적 가능성"에 더 가깝다.  
그래서 상태가 컴포넌트 맵에 명시적으로 놓이는 편이 유리하다.

### 시스템 순서가 중요한 이유

대표 순서는 아래와 같다.

1. 생존/정리
2. 점유 갱신
3. 경로탐색
4. 이동
5. 전투
6. 시야
7. 경제/생산/연구/건설
8. 승리 판정

이 순서를 어기면 아래 같은 문제가 생긴다.

- 이동이 오래된 occupancy를 참조한다
- 전투가 오래된 좌표로 판정된다
- 시야가 최신 생존 상태를 반영하지 못한다

즉, 결정론은 단순히 랜덤을 없애는 문제가 아니라, 상태 전파 순서를 고정하는 문제이기도 하다.

## 이동, 경로탐색, 점유 처리

RTS에서 가장 까다로운 축 중 하나는 "많은 유닛이 동시에 움직이는 상황"이다.

### 정적 정보와 동적 정보를 분리

- `MapGrid`는 지형의 정적 passability와 가중치를 담당한다
- `OccupancyGrid`는 유닛/건물의 현재 점유를 담당한다

이 분리는 중요하다.  
정적 맵과 동적 혼잡을 같은 구조에 섞으면 업데이트 비용과 디버깅 난도가 동시에 올라간다.

### 경로탐색 비용을 tick budget 안에 넣기

경로탐색은 정확도보다 예산 통제가 먼저다.

- tick당 path request quota
- tick당 node budget
- blocked/stuck 상황에서의 replan
- cooldown 기반 재시도

이 구조는 frame spike를 줄이고 장시간 실행에서 안정성을 확보한다.

### 왜 재경로탐색이 별도 관심사인가

RTS에서는 처음 찾은 경로보다 "막혔을 때 어떻게 회복하느냐"가 더 중요하다.  
따라서 단순 A* 구현만으로 충분하지 않고, 다음과 같은 운영 규칙이 필요하다.

- 다음 waypoint가 막히면 재계산
- 일정 시간 진전이 없으면 stuck 판단
- 과도한 재탐색으로 예산을 소모하지 않도록 cooldown 유지

## 전투와 시야

### 전투 설계 포인트

- deterministic target selection
- overkill 완화
- sticky target 유지
- attack-move, hold, patrol 같은 상위 명령과 결합

전투에서 중요한 것은 단순 DPS 계산이 아니라 "많은 유닛이 동시에 판정될 때도 결과가 흔들리지 않는 것"이다.

### 시야는 UI 기능이 아니라 규칙 계층

안개와 시야는 렌더링 연출이 아니라 정보 은닉 규칙이다.  
즉, snapshot에 무엇을 넣고 클라이언트에 무엇을 보여줄지의 기준점이 된다.

이 원칙을 지키면 다음이 가능하다.

- 서버가 노출 가능한 정보만 보내도록 설계
- 클라이언트가 비가시 정보를 몰래 보지 못하도록 경계 설정
- replay/snapshot의 의미를 일관되게 유지

## 경제, 건설, 생산, 연구

RTS의 전략성은 전투만으로 생기지 않는다.  
자원과 생산 시스템이 있어야 의사결정의 축이 만들어진다.

### 경제

- 자원은 faction stockpile로 유지
- worker는 자원을 즉시 소모시키지 않고 cargo를 운반
- drop-off 시점에 stockpile이 증가

이 흐름은 채집 애니메이션이 없어도 경제 사이클을 명확히 만든다.

### 건설

- footprint 기반 배치
- clearance 규칙
- builder assignment
- progress 완료 전까지 기능 비활성
- 취소/환불 규칙

이 구조는 "건물은 즉시 생성된다"는 단순 모델보다, RTS다운 시간 비용과 공간 점유를 더 명확히 반영한다.

### 생산과 연구

- 생산은 building queue 기준
- queue limit, producer capability, rally offset이 데이터 기반
- 연구는 faction unlock 상태를 전역적으로 갱신

즉, 규칙을 하드코딩만 하지 않고 데이터 주도 구조로 점차 이동하고 있다.

## `server` 계층 설계

### 역할

서버는 판정을 직접 새로 구현하지 않는다.  
핵심 역할은 아래와 같다.

- 연결 수립과 handshake 처리
- room lifecycle 관리
- 입력 검증과 큐잉
- tick 단위 sim 진행
- snapshot/ack/replay 생성

이 계층은 "권위(authority)"를 갖지만, 규칙 그 자체의 원천은 `sim`이다.

### 입력 검증을 별도 계층으로 두는 이유

네트워크 경계에서는 규칙 이전에 먼저 막아야 할 문제가 있다.

- 크기 제한
- 빈 값/공백
- batch cap
- stale/future tick window
- 소유권 위반
- 범위 밖 좌표
- unsupported command
- pending queue 과적

이 검증이 없다면 sim 규칙이 맞아도 서버는 운영상 불안정해진다.

### resume token 지원의 의미

재연결은 편의 기능처럼 보이지만, 실제로는 운영 안정성과 직접 연결된다.

- 일시적 네트워크 끊김에서 세션 복구
- room 상태와 플레이어 identity의 분리
- 서버가 세션 만료 창을 통제

이 기능은 향후 실제 멀티플레이 품질을 높일 수 있는 기반이다.

## `client` 계층 설계

클라이언트는 크게 세 종류다.

- 인터랙티브 CLI
- 봇 클라이언트
- 그래픽 클라이언트

이 셋을 나누는 이유는 역할이 다르기 때문이다.

### CLI 클라이언트

- 프로토콜 디버깅과 빠른 검증에 유리
- 텍스트 HUD로 상태 추적 가능
- 스크립트 입력으로 재현성 높은 수동 테스트 가능

### 봇 클라이언트

- 서버 종단 smoke에 사용
- 사람 개입 없이 match completion 경로 검증
- replay 기록과 match-end 검증에 적합

### 그래픽 클라이언트

- snapshot 소비와 렌더링 구조를 검증
- 실제 플레이 감각과 입력 피드백 점검
- UX 개선의 기반

## `shared-protocol`과 계약 관리

멀티언어, 멀티모듈 프로젝트에서 가장 위험한 부분은 "서로 같은 메시지를 다르게 이해하는 것"이다.  
`starkraft`는 이를 줄이기 위해 세 단계를 둔다.

1. schema
2. golden payload
3. 언어별 model + test

이 구조의 장점:

- 문서와 구현이 분리되지 않는다
- breaking change 범위를 빨리 파악할 수 있다
- CI에서 계약 회귀를 자동으로 잡기 쉽다

## `tools` 계층 설계

이 프로젝트에서 도구는 부가 기능이 아니라 검증 계층이다.

### replay 도구

- metadata 확인
- 통계 집계
- hash 검증
- fast-forward 재실행
- server NDJSON keyframe 검증

### map/data 도구

- 맵 생성/검증
- 유닛/건물/기술 데이터 cross-reference 검증
- JSON output contract 제공

이 도구 계층 덕분에 데이터와 운영 산출물도 코드처럼 검증할 수 있다.

## 테스트 전략의 기술적 의미

테스트가 많다는 사실보다 더 중요한 것은 "무엇을 지키기 위한 테스트인가"다.

`starkraft` 테스트 전략의 중심은 아래 두 가지다.

1. 결정론이 깨지지 않는가
2. 네트워크 경계에서 잘못된 입력이 통제되는가

그래서 일반 기능 테스트 외에 아래가 중요하다.

- determinism test
- replay rerun test
- protocol round-trip test
- smoke scripts
- replay verifier
- soak/benchmark harness

## 운영 문서가 중요한 이유

개인 프로젝트에서도 운영 문서를 두는 이유는 명확하다.

- 서버를 어떻게 띄우는지
- 상태를 어디서 보는지
- replay를 어떻게 검산하는지
- 릴리스 산출물을 어떻게 고정하는지

이런 정보가 문서화되어 있으면 프로젝트는 "실험 코드"에서 "관리 가능한 시스템"으로 넘어간다.

## 현재 기술적 부채와 다음 우선순위

### 현재 부채

- 그래픽 클라이언트 UX와 구조 분리가 더 필요함
- 장시간 네트워크 운영 시나리오 데이터가 더 필요함
- 밸런스 문서와 실제 데이터의 장기 동기화 체계가 아직 약함

### 다음 우선순위

1. 그래픽 클라이언트의 view model / renderer 분리 강화
2. 장시간 세션 soak와 운영 관측성 확대
3. 프로토콜/리플레이 장기 호환성 정책 강화
4. 데이터 정의와 문서 자동 동기화 개선

## 결론

`starkraft`의 기술적 핵심은 화려한 기능 수가 아니라 아래에 있다.

- 규칙 엔진을 결정론적으로 유지하는 구조
- authoritative server로 입력을 통제하는 경계 설계
- replay와 hash를 품질 자산으로 쓰는 검증 문화
- 문서, 코드, 테스트, 운영 루트를 하나의 시스템으로 묶는 방식

이 점이 이 프로젝트를 단순 RTS 프로토타입이 아니라, 엔지니어링 설계 역량을 보여주는 저장소로 만든다.
